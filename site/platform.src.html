The platform

Change the rules like software. Run the data like a query.

Every configuration change a fund makes is a reviewed, versioned, atomic commit. Every trade, price and accrual is processed against one pinned version of that configuration — and because the configuration is pinned, the entire calculation is knowable before a single byte moves.

The split that makes the rest possible

A control plane for decisions. A data plane for volume.

Most accounting systems fuse the two: the rules live inside the engine, so changing a rule means changing the thing that is currently processing your data. Ratio separates them completely.

Control plane · how the fund works

Decisions, versioned

  • Posting rules, fee schedules, accrual conventions, account mappings, valuation policy, calendars, entitlements.
  • Authored, reviewed and approved like code — proposed, diffed, checked, merged.
  • Every version is content-addressed: an immutable artifact identified by its own hash.
  • Handles no market data and processes no transactions. It cannot be the reason a number is wrong at volume, because it never touches volume.

Data plane · what actually happened

Facts, processed

  • Trades, prices, FX, corporate actions, cash movements, positions, tax lots.
  • Every run names the exact configuration version it executed under and cannot silently pick up another.
  • Append-only. Nothing is amended in place; corrections are new facts with their own provenance.
  • Defines no policy. It cannot invent a rule, only apply the one it was handed.

What that buys you

Version control, for the way the fund is run

Software teams stopped editing production twenty years ago. Fund operations largely did not — configuration still tends to live in screens that authorized people change, with an audit log bolted on afterwards. Ratio treats a rule change the way an engineer treats a release.

Proposed, not applied

A change starts as a proposal against the current version. It is reviewed and approved by name before it is anywhere near a calculation — and until it is approved, nothing in the data plane can see it.

Atomic

A version is promoted whole or not at all. There is no window in which half a fee change has taken effect, and no run that catches a configuration mid-edit.

Diffable

Two versions can be compared line by line, and — more usefully — the same day's data can be run under both, so you see the change in the numbers before you commit to it rather than after.

Attributable

Every posting, position and NAV carries the hash of the configuration that produced it. "Which rules generated this figure?" resolves to one immutable artifact, not to an archaeology exercise.

Reversible

Rolling back is moving the pointer to the previous version. It is not a data migration, an unwind script, or an overnight batch — because no historical record was mutated in the first place.

Interface concept — not a shipped product. See the roadmap for what exists today.

Authoring

From what an expert says to what the books enforce

The scarce thing in fund accounting is not compute — it is the person who knows precisely how this fund's fees, accruals and classifications actually work. Ratio's job is to get that knowledge into the system without an eighteen-month implementation project, and without trusting a language model with your books.

Stage one

The expert says it

In their own words, in a review call, exactly as they would explain it to a new analyst.

“Management fee accrues daily on the prior day's net assets at 75 basis points a year, actual/365. Payable quarterly in arrears. Don't accrue on a non-business day — roll it into the next one.” Fund controller, onboarding session
Stage two

The model drafts it

A language model turns that sentence into a precise, typed, declarative rule. This is the only step it performs, and it is a drafting step.

rules/management_fee.ratiodraft
rule management_fee_accrual {
  when       business_day d
  basis      net_assets(d.previous)
  rate       75bp / year
  day_count  ACT/365
  posts      debit   expense.management_fee
             credit  liability.management_fee_payable
  settles    quarterly in_arrears
  on_holiday roll_forward
}
Stage three

The grounding checks it

The draft is compiled and every obligation it implies is discharged mechanically. This is the step that makes the previous one safe.

  • The posting nets to zero on every dimension — the kernel would refuse it otherwise, so this cannot be got wrong later.
  • Both accounts exist in the chart, and their normal balances match the direction the rule assumes.
  • net_assets(d.previous) resolves to a recorded fact with provenance, not a live lookup that could return a different answer on replay.
  • Rate and day-count are typed quantities — 75bp/year under ACT/365 — not floating-point constants.
  • No effect on any closed epoch.
  • roll_forward needs a holiday calendar, and the fund has two. Which one governs settlement? The question goes back to the expert; nothing is guessed.

This is the whole trick. The model is allowed to be wrong, because everything it produces is checked against structure it cannot influence — the chart of accounts, the epoch calendar, the type system, and the balancing rule the kernel proves. An error surfaces as a failed check or a question, in review, before anything is approved. It cannot surface as a wrong number in a client's statement.

Stage four

It becomes a version

Approved, the rule is frozen into a content-addressed configuration — and from that moment the data plane can execute it.

promote 7d2b904committed
config@6b0d41f → config@7d2b904

  + rule     management_fee_accrual
  + dep      calendar us_settlement   (answered: US settlement)

  epoch      Q4-2026     effective 2026-10-01
  authored   model draft, reviewed line by line
  approved   J. Okafor (controller), A. Mensah (fund accounting)
  checks     6 passed · 1 question resolved

  every posting produced under this version will carry
  the hash 7d2b904 for as long as the fund exists

Weeks, not quarters. The bottleneck in a conventional implementation is translating domain knowledge into a vendor's configuration language, by consultants, over months. Here the expert speaks, the model drafts, the compiler interrogates, and a human approves — and what lands is stricter than what a consultant would have typed, because it had to satisfy the checks to get in.

Striking NAV

A NAV calculation is a query plan. So plan it.

Valuing a fund is a large conditional graph — scans over lots, prices, FX rates, calendars and corporate actions, joined and filtered and aggregated, with branches everywhere: if this security type, if this lot is wash-sale affected, if this share class, if this jurisdiction. Structurally it is a SQL query tree.

Conventional engines interpret that tree, one position at a time. Each branch discovers what data it needs while it is running, so fetching and computing interleave — and the run is spent waiting on round-trips it could not see coming.

Ratio compiles it instead. Because the configuration is pinned and immutable for the epoch, the entire graph is fully determined before the run starts. Every scan it will ever need can be identified up front, hoisted out of the conditionals, and issued as one batched parallel fetch. Only then does any arithmetic happen.

What the planner knows that a query optimizer doesn't

A database planner estimates from table statistics. Ratio's planner has something better: the same fund struck NAV yesterday, and roughly two hundred and fifty times before that, under a configuration that barely changed.

Measured history, not estimates

Actual cardinalities, actual selectivities, actual per-source fetch latencies — recorded from previous runs of a nearly identical graph rather than guessed from a histogram.

Branch prediction, at fund scale

Which conditional arms will actually be taken — which lots hit the wash-sale path, which securities have a corporate action pending, which share classes trigger the tiered fee. Scans for branches that will be taken are issued speculatively; scans for branches that will not are skipped entirely.

Partitioning that balances

Lots are grouped so that each partition's working set is roughly equal and shares its price, FX and calendar dependencies — so the fetch coalesces and no worker finishes early while another still has a third of the book.

It is only ever an optimization

A wrong prediction costs time, never correctness: a missed scan is fetched on demand and a useless one is discarded. The kernel still checks that every entry balances, whatever order the data arrived in.

Why it parallelizes so well

Resolve the branches at plan time, and what's left is arithmetic

Hoisting the scans has a second consequence, and it is the more important one. If every conditional is decided while planning — because the configuration is pinned, so which rule applies to which lot is knowable in advance — then the thing handed to the engine is not a branchy program over irregular objects. It is a flat array of fixed-width records, with the decisions already baked in as data: each lot arrives carrying its rate, its day-count, its accounts, its dimension indices.

That is the difference between a workload that fights parallel hardware and one that was made for it. Identical instructions, no divergence, no pointer chasing, uniform stride. And the fold is associative and commutative — a proved property of the kernel, not an assumption — so partial sums combine in any order. An associative reduction over a uniform array is the single friendliest shape in all of parallel computing.

The arithmetic, shown

Twenty million tax lots, and the accounting is the cheap part

A large index-fund complex might carry twenty million open tax lots. On the incumbent stack that book is roughly an hour of overnight processing. Here is the same run costed from the kernel's own per-record work, so you can check it rather than take it.

The honest headline is ten to fifteen minutes, not ten seconds. The valuation itself is genuinely milliseconds — but a NAV run has to get its data out of custodians, pricing vendors and fund administrators, and those are other people's systems running at other people's speeds. That is the floor, and no amount of engineering on this side of the wire moves it.

Why the distinction matters more than the total. An interleaved engine spends its hour with the two costs braided together, so neither can be attacked: you cannot batch the IO because you do not know what you need until you are computing, and you cannot parallelize the compute because it is blocked on the IO. Separating them does not make the feeds faster. It makes everything else disappear — and it means the expensive hardware is only rented for the seconds it is actually working.

Where the data lives

No database license underneath any of this

It is easy to make a batch job look cheap by quoting the compute and quietly running it on top of a six-figure relational estate. That is the usual shape of this industry's cost base — an enterprise RDBMS, its per-core licensing, its storage tier, and the people who keep it alive — and it is where the money actually goes.

Ratio does not have one. The system of record is the append-only log itself, kept as compacted columnar files on ordinary object storage. There is no query engine to license, no per-core bill, and no vendor with pricing power over your own history.

The log is the database

Facts and postings are immutable and append-only, which is precisely the access pattern object storage is best at and the one relational engines are worst at. Nothing is updated in place, so there are no locks, no vacuum, no index maintenance, and no migration window.

Compaction at epoch boundaries

At the close of each accounting epoch the log is folded into a columnar snapshot. Replaying a period reads that snapshot plus a short tail rather than re-folding from the beginning of the fund's life — so replay cost stays flat as history grows.

Tiering follows the epoch calendar

The open epoch sits hot; recent closed epochs sit in standard storage; epochs retained only to satisfy a seven-year obligation sit in archive-class storage at a fraction of a cent per gigabyte. The system already knows which is which — the epoch is a first-class concept, not a date column someone has to write a lifecycle policy against.

Columnar layout is what makes the fetch predictable

The planner knows which columns and which partitions a run needs, so it reads exactly those. This is the same property that lets the scans be hoisted in the first place: predictable reads and cheap storage are the same design decision.

Content addressing dedupes for free

Configuration artifacts are identified by hash, so a rule set shared across fifty funds is stored once, and an unchanged epoch costs nothing to keep referencing.

So the close is fast. So what?

A valuation you can afford to run a thousand times is a different instrument entirely

Making a nightly batch finish sooner is a nice operational win and not much more. The interesting consequence is elsewhere, and it is easy to miss because the constraint has been in place so long that the industry has built its whole shape around it.

Because an exact valuation is expensive, nobody uses the exact valuation to make decisions. They use something else: a risk system with its own position store, a pre-trade checker with a simplified tax model, an attribution engine with its own price history, a spreadsheet on a PM's desk. Each is a fast approximation of the book, maintained separately, and each drifts.

An enormous amount of work in this industry exists to reconcile those approximations back to the book of record — and every discrepancy between them is a decision that was made on a number that was not quite true.

Today — two systems, permanently drifting

Fast and wrong, or exact and late

  • The book of record is exact, auditable — and available tomorrow morning.
  • So every decision made during the day is made against a model of the book, not the book.
  • The model has its own positions, its own prices, its own simplifications of tax and fees.
  • Reconciling the two is somebody's permanent job, and the gap is where bad decisions live.

When exact costs two cents

One system, asked repeatedly

  • The exact valuation is the fast one. There is no second model to maintain or reconcile.
  • Every answer is a real, balanced, auditable set of books — not an approximation of one.
  • Any question you would have approximated, you now simply run.
  • The reconciliation between model and book disappears, because there is no longer a model.

What that turns NAV into

A continuous reading, not a nightly event

Strike it hourly, or on every material market move. Know what the fund is worth now — exactly, with the fee accrual and the tax position included — rather than knowing what it was worth last night.

Pre-trade impact, against the real book

“What does this basket do to NAV, to the tax position, to the fee accrual, to every share class?” Answered by running the actual close over the actual ledger with the trade in it — so the answer cannot disagree with tonight's books, because it was produced by the same engine under the same pinned configuration.

Tax-lot selection as a search, not a heuristic

Choosing which lots to sell is an optimization problem that firms currently solve with rules of thumb because evaluating a candidate is expensive. At two cents an evaluation, you can search thousands of harvesting strategies against the real ledger and take the best one.

Stress and scenario at book fidelity

Shock the prices, the curve, the FX — and re-run the genuine close, thousands of times in parallel. Each scenario produces a complete, balanced, inspectable set of books rather than a risk number whose derivation nobody can reproduce.

Rule changes tested before they ship

The control plane already lets a proposed configuration run against real data. Cheap valuation makes that routine: replay years of closes under a proposed fee schedule or accrual convention and see precisely what it would have done, before approving it.

Reconciliation that never stops

Rather than hunting breaks at month-end, run continuously against the custodian feed and surface a break within the hour it appears — while the person who caused it still remembers the trade.

The claim in one line: every other platform makes you choose between a number that is fast and a number that is true. Make the true one fast and the choice disappears — along with the second system, the drift between them, and the reconciliation that has been quietly taxing the whole industry for thirty years.

Integrations and applications

One contract, and everything else is an application

Because the trusted core is small and closed, everything else can be open. Data comes in as typed facts with provenance; capability goes out over one documented API; and neither can violate the balancing rule that the kernel enforces.

Custodian & administrator feeds

Positions, transactions and cash from custodians and fund administrators, normalized into facts that carry their source, retrieval time and validity window.

Fact plane

Market data

Prices, FX, corporate actions and reference data. Recorded as of a point in time, so a late arrival is a new fact rather than a silent rewrite of yesterday.

Fact plane

Portfolio accounting

Positions, tax lots, multi-currency, P&L. The only tier inside the proven core, and deliberately the smallest.

Trusted core

Fees & billing

Accrual schedules, tiered and blended rates, waivers, rebates — authored as rules in the control plane, executed as ordinary postings.

Control plane

Trading & rebalancing

Models, drift, tax-aware lot selection. Proposes transactions; the core still checks each one before it lands.

Control plane

Performance & reporting

Time- and money-weighted returns, attribution, GIPS-oriented composites — computed over an immutable history that can be replayed.

Analytical

Client & advisor portals

Statements, dashboards and documents, reading the same API any third party can read. No privileged back door into the ledger.

Presentation

Compliance & surveillance

Restrictions and mandates expressed as control-plane rules, with the evidence trail falling out of the versioning rather than being assembled for an examiner.

Control plane

Risk & scenario analysis

Runs the real engine against hypothetical facts or an alternative configuration, which is what makes a what-if trustworthy rather than a separate model that drifts.

Analytical

CRM & practice systems

Connectors rather than a rebuild. Ratio has no ambition to be your CRM — it has an ambition to be the thing your CRM can trust.

Extension

Your own code

Extensions in ordinary languages against a documented gRPC contract, with data exportable in open formats. The extension surface is wide precisely because the trusted core is narrow.

Extension

Authoring assistant

Drafts rules, explains figures, proposes reconciliations. Fenced above the trust boundary; every output is checked before it can affect anything.

Fenced

Tiers are the same taxonomy used in the component specifications behind the roadmap: what sits inside the proven core, what merely feeds it, and what is built on top. Almost everything is on top — that is the design working, not a gap in it.

Small proven core. Everything else, open.

Versioned decisions, planned execution, and a boundary between them that a mistake cannot cross.
